# R6.5.3g — Stock-only scientific HTTP/3 workload planner

R6.5.3g converts the frozen scientific workload definitions and the qualified
DUT→load-generator network service envelope into an immutable execution plan.
It is a qualification/planning stage, not a stock-vs-NGI541 performance claim.

## Anti-bias rule

Only the stock OpenSSL NGINX binary may participate in target-rate,
concurrency, worker, pacing or coverage calibration. `ngi541-direct` is not
started by the planner. Later paired campaigns must consume the frozen plan
unchanged for both variants.

## Inputs

The planner resolves the latest compatible COMPLETE artifacts for:

- R6.5.3c network evidence and its directional service envelope;
- R6.5.3b pinned HTTP/3 `h2load` runtime;
- R6.5.3d scientific corpus;
- R6.5.3e HTTP/3/TLS security gate;
- R6.5.3f dual-host telemetry capability qualification.

Resolved artifact hashes, the stock NGINX SHA-256, DUT physical-core count and
load-generator logical CPU count are part of the planner input identity.
Re-running with byte-identical resolved inputs reuses the existing frozen plan
instead of probing again.

## Service targets

The canonical planning targets are 50% and 80% of the empirically qualified
DUT→load-generator service envelope. For a fixed object of size `B` bytes:

```
aggregate_object_rate_hz = target_mbps * 1,000,000 / (8 * B)
per_client_rps = aggregate_object_rate_hz / connections
```

`h2load --rps` is explicitly per client, so the division by the number of
connections is part of the plan contract.

CLAS12 and LCLS use application-paced fixed-object requests. HACC uses a
byte-paced timing script over a deterministic bounded calibration subset. The
HACC calibration subset is **not** a full HACC dataset performance claim; it is
used only to derive transport concurrency without requiring local
materialization of multi-gigabyte objects. The scientific HACC profile and its
full/deterministic-stratified/time-window coverage contracts remain unchanged
for later capable environments.

## Concurrency search

Candidates are evaluated in the exact order listed in the configuration. The
first candidate that satisfies every gate is selected; candidates are not
ranked retrospectively by performance.

A candidate must:

- sustain at least 95% of prescribed application goodput;
- complete without failed/errored/timed-out requests;
- keep load-generator total CPU below 85%;
- keep every load-generator core below 95%;
- show no Raspberry Pi firmware throttling;
- show no DUT thermal/performance throttling.

Failure to find a qualifying candidate is fatal. The target is never lowered to
make a run pass.

## Workers

Two semantic server points are frozen:

- `single` → one NGINX worker;
- `physical-core-count` → the DUT physical-core count resolved at planning time.

These are independent of network bandwidth.

## Telemetry during probes

Every stock calibration probe captures actual dual-host telemetry. DUT process
CPU time can later be expressed as CPU-seconds/GiB, and same-host estimated
package power can be integrated to estimated J/GiB when available. These values
are qualification evidence only and are not a stock-vs-NGI541 claim.

The planner consumes h2load 1.69 JSON output for application bytes and QUIC
statistics. qlog is disabled in the frozen performance plan by default to avoid
instrumentation perturbation; it can be enabled by a separate diagnostic run.

## Output

```
qualifications/workload-planner/<qualification-id>/
├── definition.json
├── inputs/resolved-inputs.json
├── raw/
├── processed/
│   ├── calibration-corpus.json
│   ├── probe-results.json
│   ├── workload-plan.json
│   ├── summary.json
│   └── SUMMARY.md
└── artifacts.sha256
```

`workload-plan.json` is the contract consumed unchanged by the subsequent
paired stock/NGI541 stage.

## Command

```bash
./scripts/experiment.sh workload-planner \
  --config benchmark/configs/r6.5.3g-pi-mac-stock-workload-planner.json
```
