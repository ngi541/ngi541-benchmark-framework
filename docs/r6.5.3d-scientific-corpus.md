# R6.5.3d — Deterministic Scientific Corpus and HACC Coverage Model

## Scope

R6.5.3d converts the frozen scientific profiles from R6.5.3a into deterministic,
machine-readable corpus definitions. It does not execute HTTP/3 traffic and it
does not adapt scientific object semantics to the current network topology.

The output separates three concerns:

1. **scientific profile** — what the real scientific workload represents;
2. **deterministic corpus** — how repeatable surrogate bytes and logical objects
   are defined;
3. **coverage** — which part of a corpus a later execution plan selects.

This separation allows the same CLAS12, LCLS and HACC corpus identities to be
used on the current Pi/Mac path, a later wired topology and CloudLab without
changing the scientific workload definitions.

## Deterministic content

All surrogate payloads use `splitmix64-v1`. The per-object 64-bit seed is
obtained from SHA-256 over:

```text
seed namespace || NUL || scientific profile SHA-256 || NUL || object id
```

The first 64 bits of that digest are interpreted as an unsigned big-endian seed.
SplitMix64 words are serialized little-endian. Therefore object bytes are a
pure function of profile identity, object id and object size.

Chunking during materialization does not alter content. A 10 MB LCLS frame
materialized in 1 KiB chunks and the same frame materialized in 1 MiB chunks
must be byte-identical.

The corpus manifest stores a **content recipe SHA-256**, not a claim that the
full multi-terabyte HACC dataset has been physically materialized and hashed.
Actual SHA-256 is produced whenever a concrete object is materialized.

## Indexed stream corpora

CLAS12 and LCLS remain indexed streams rather than finite pre-generated files.

```text
CLAS12
  semantic unit: event
  object bytes: 32,768
  object ids: event-000000000000, event-000000000001, ...

LCLS
  semantic unit: detector frame
  object bytes: 10,000,000
  object ids: frame-000000000000, frame-000000000001, ...
```

Each index receives a different deterministic content seed. Later workload
planning chooses how many indexed objects are needed for a time window or an
explicit object count. The profile object size itself is never scaled to fit a
network.

## HACC logical dataset construction

The HACC profile contains the published 19,260-object size histogram, exact
logical byte total and published minimum/maximum object sizes. The publication
does not specify every individual file size inside each histogram bucket, so
R6.5.3d deliberately does not invent a hidden empirical distribution.

Instead it uses a transparent constrained deterministic allocation:

```text
algorithm = capacity-weighted-largest-remainder-v1
```

The procedure:

1. creates exactly the published object count in every normalized histogram
   bucket;
2. fixes one object to the published smallest size and one to the published
   largest size;
3. caps every generated object at the published largest object size;
4. derives a stable object-specific SHA-256 weight and distributes the remaining
   published logical byte total over each object's legal capacity using those
   weights; this creates deterministic within-bucket variation without claiming
   knowledge of the unpublished original file sizes;
5. resolves capacity saturation and integer remainder bytes deterministically;
6. verifies the final sum equals exactly 4,442,781,786,482 bytes.

Logical object order is independent of bucket layout and is fixed by
`sha256-object-key-v1` using the scientific profile seed namespace.

The result is a deterministic scientific surrogate constrained by every
published aggregate HACC invariant available to the framework. It is not
presented as a reconstruction of unknown original per-file sizes.

## HACC coverage modes

The corpus supports all three coverage modes frozen in the R6.5.3 design.

### `full`

Selects all 19,260 logical objects and all 4,442,781,786,482 logical bytes.
Physical materialization is still lazy; selecting full coverage does not imply
that R6.5.3d writes 4.4 TB to disk.

### `deterministic-stratified`

Selects an explicit object count while preserving representation across all
non-empty published histogram buckets.

The contract is:

```text
at least one object from every non-empty bucket
published smallest object included
published largest object included
bucket quotas derived by largest remainder from published populations
within-bucket object selection deterministic
final execution order follows canonical HACC object order
```

This mode is intended for bounded qualification or experiment windows that need
coverage of the entire published file-size range without falsely claiming a
full-dataset transfer.

### `time-window`

The caller supplies duration and target application goodput. The byte budget is:

```text
ceil(duration_seconds * target_goodput_mbps * 1,000,000 / 8)
```

HACC coverage takes the canonical ordered prefix until cumulative logical bytes
meet or exceed that budget. Any one-object overshoot is retained and reported.
If the entire logical dataset is smaller than the requested budget, the result
reports dataset exhaustion instead of looping silently.

For CLAS12/LCLS the same byte budget is converted to a contiguous indexed-stream
object count using the fixed scientific object size.

## Generated artifacts

The canonical command is:

```bash
./scripts/experiment.sh scientific-corpus \
  --config benchmark/configs/r6.5.3d-scientific-corpus.json
```

The output is content-addressed rather than timestamp-addressed:

```text
corpora/scientific/<corpus-id>/
├── definition.json
├── processed/
│   ├── registry.json
│   ├── coverage-contract.json
│   ├── summary.json
│   └── profiles/
│       ├── clas12-event-stream-v1.corpus.json
│       ├── lcls-detector-frame-v1.corpus.json
│       └── hacc-multifile-dataset-v1.corpus.json
└── artifacts.sha256
```

The corpus id is derived from both the semantic corpus definition and the
resolved SHA-256 identities of every selected scientific profile. The same
frozen inputs therefore produce the same corpus id and the same corpus manifests. An existing matching corpus is verified through `artifacts.sha256`
and reused rather than regenerated under a new timestamp.

## Non-goals

R6.5.3d does not:

- use the R6.5.3c network envelope to change scientific object sizes;
- choose HTTP/3 connections, streams, workers or offered rate;
- materialize the full 4.4 TB HACC logical dataset;
- claim that deterministic surrogate bytes are original detector/simulation
  bytes;
- make a stock-vs-NGI541 performance claim.

Those execution decisions belong to later R6.5.3 planning and qualification
stages.
