# R6.5.4 — controlled paired scientific workload execution

R6.5.4 is the first performance-measurement stage after the complete R6.5.3 freeze. It consumes the exact R6.5.3h final manifest and the byte-identical R6.5.3g workload plan for both `stock` and `ngi541-direct`.

## Experimental design

- 12 frozen conditions (3 scientific profiles × 2 service targets × 2 worker semantics).
- 4 paired repetitions per condition.
- 48 stock↔NGI541 pairs / 96 variant runs.
- Rotating condition order across repetition rounds.
- Balanced-by-condition-round variant order: every condition has 2 stock-first and 2 NGI541-first pairs.
- No adaptive replanning after freeze.
- No candidate-variant tuning.
- No metric-dependent retry.
- No metric-dependent outlier deletion.

A low achieved goodput for either variant is a performance result. It is not used to invalidate or repeat a run. Validity failures are restricted to measurement integrity conditions such as HTTP errors, load-generator saturation, or throttling.

## Telemetry window

The h2load workload retains the frozen 5 s warm-up and 20 s measurement interval. Raw DUT and load-generator telemetry are retained for the complete run. Resource-efficiency summaries use samples after the warm-up boundary, so CPU-seconds/GiB and estimated J/GiB correspond to the measurement window rather than including startup warm-up work.

## HACC scope

The local R6.5.4 campaign repeats the exact bounded HACC subset used by the frozen planner. This preserves the client shape selected before candidate execution and avoids a post-freeze workload change. It is explicitly **not** a full 4.44 TB HACC dataset-completion claim. Broader/full HACC coverage belongs to later dedicated-hardware campaigns.

## Primary metrics

- scientific/application goodput (Mbit/s), higher is better;
- DUT NGINX process CPU-seconds/GiB, lower is better.

Secondary metrics include same-host estimated package energy J/GiB when available, load-generator headroom, UDP errors, and thermal/throttling validity.

Paired percent deltas are reported with a single convention: positive values favor `ngi541-direct`. No pair is removed as an outlier.

## Operational resume

A campaign interrupted before all 96 scheduled runs complete is resumed using already persisted valid `run-result.json` records. Completed runs are never repeated. A run that produced an invalid result is not retried under the same campaign. Re-execution is therefore limited to an operationally incomplete run for which no completed result exists; it is never selected based on the observed performance metric.
